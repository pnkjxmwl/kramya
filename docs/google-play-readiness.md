## Concrete privacy defect: push registration survives sign-out

**High priority before real users.** `apps/native/app/src/main/java/app/kramya/net/Models.kt:479` defines `LogoutRequest` with only `refreshToken`. `net/Auth.kt:103–110` sends that object on sign-out. The API in `apps/api/src/modules/auth/auth.controller.ts:104–106` unregisters the device only when `body.pushToken` is supplied. No alternative native unregister path was found.

Consequently, clearing the local login does not remove the server's push-device association. `NotificationsService.dispatch()` sends pending alerts to enabled tokens, and FCM notification payloads can be displayed by Android while the app is in the background. A phone can continue showing the old account's queue/clinic alerts after logout. The source establishes the missing unlink; delivery after logout was not reproduced on a device during this assessment. Re-registering under another account moves the token, but that does not cover the signed-out interval or a failed registration.

Fix the Kotlin logout contract/integration to unlink its device token, clear delivered notifications and pending notification navigation, and handle offline logout explicitly. Verify foreground/background delivery, logout, account switching and token rotation with two fictional accounts. Add regression coverage for the client payload and server unlink. This is a data-handling issue, not merely a notification styling issue.

## Production launch gates beyond the submission forms

These are product/operational acceptance gates, not claims that Google mandates a particular cloud provider or paid plan.

1. **Separate production from fictional staging.** `apps/native/gradle.properties` currently sends release builds to the same Render API used for TEST clinics/payments. Establish an explicit environment boundary, prevent ordinary patients seeing fake clinics, and prevent testing from touching real records. Keep the existing monolith and tenant isolation; a microservice rewrite is unnecessary for this work.
2. **Make real consultation payments operational.** Razorpay TEST success/failure is proven, not live merchant readiness. Verify merchant activation, live key/webhook matching, receipts, refund delivery, delayed capture, duplicate notifications and interrupted checkout before accepting money. Show cancellation/refund terms before payment and provide an effective support route. In-person consultations are physical services: retaining Razorpay fits the physical-service exclusion from Play Billing, based on the current product model. Reassess if digital subscriptions/features are later sold. [Payments policy](https://support.google.com/googleplay/android-developer/answer/9858738).
3. **Complete the clinic journey.** Run reception check-in, doctor call/start/complete, skip/recall, cancellation/refund and socket reconciliation across the real staff console and Kotlin app. Existing automated checks and one successful checkout are not this full acceptance proof. Use [TESTING.md](../TESTING.md); demo UI remains excluded.
4. **Prove notifications and recovery.** Test foreground/background/locked/terminated process delivery, permissions denied, expiry, network changes and account switching. Distinguish a terminated process from Android Settings Force stop, which affects delivery differently. Fix the logout issue above. Never present stale queue data as current.
5. **Make the ETA promise defensible.** Conduct the supervised one-clinic pilot in [the ETA guide](pilot-eta-validation.md); measure waiting outcomes as well as error, tune on one cohort and validate on held-out days. Use uncertainty and fallback instructions; do not promise exact arrivals or zero waiting. Avoid implying emergency or clinical triage functionality.
6. **Resolve recoverability and availability.** UptimeRobot is monitoring, not evidence that workers, sockets and notifications will operate reliably throughout clinic hours. Demonstrate those behaviors and train reception in a fallback process. Manual encrypted recovery exists. Scheduled backups/retention automation/backup alerts remain deferred at the founder's request; this review does not activate them or authorize a paid plan. Patient-data retention/deletion policy is a separate requirement and still needs definition.
7. **Finish essential user support and accessibility.** No self-service password reset was found in native or API auth; add a secure, expiring, single-use recovery flow with generic responses and rate limits. Add Help, privacy, deletion and payment/support contact entry points. Finish small screens, large text, TalkBack, keyboard, loading/offline and permission-denial testing. Password reset and a particular colour scheme are not standalone Play form requirements, but users need to recover access and obtain help.

## What is already in place, and what remains unverified

- `app/build.gradle.kts:51–59` sets compile/target **API 36**, minimum API 26. It meets the current new-submission target requirement checked on this date; recheck at submission. [Target API policy](https://support.google.com/googleplay/android-developer/answer/11926878).
- Release packaging refuses missing signing/Firebase configuration and non-HTTPS API URLs. Debug cleartext permission is in the debug manifest. Keystore-backed encrypted token storage, server token rotation and server-authoritative payment confirmation exist. These are source findings, not a security certification.
- Prior checkout work passed 50 Android JVM tests, focused API regressions and full CI; TEST checkout success/failure were exercised on the physical phone. The final Play-signed build, pre-launch report and device matrix have not been tested.
- Kotlin-only source does **not** mean the artifact has no native libraries: the existing AAB includes `libandroidx.graphics.path.so`. Its arm64-v8a and x86_64 ELF load segments were inspected and each had 16,384-byte alignment. `zipalign -c -P 16 4` passed on the existing release APK (exit 0). Those older artifacts are not the final release; rerun bundle/package checks and a 16 KB device/emulator test on the new one. [Android page-size guidance](https://developer.android.com/guide/practices/page-sizes).
- Release vital lint in the older build artifact reports no issues; a current full lint/pre-launch report is still needed. No new build, general regression suite, Play account/dashboard review, live-payment transaction or notification send was performed for this assessment.

## Recommended execution order

1. Confirm the business/legal owner and health classification; start organization/D-U-N-S verification because it can proceed while coding.
2. Fix push unlink on logout; add account deletion/request fulfilment, privacy disclosures, support and password recovery.
3. Establish the production/staging boundary and finalize payment/refund and retention operations.
4. Prepare a current signed AAB, Play App Signing, listing assets, accurate declarations and maintained review access. Use actual native screenshots with fictional information, not web demo screens or invented clinic partnerships.
5. Distribute through **internal testing**, then a controlled closed clinic test. Run the Play pre-launch report plus physical-device and patient/staff acceptance; fix failures and record tester feedback.
6. Complete the supervised ETA pilot, then use a limited initial production rollout with support and monitoring.

For clarity: the **12 testers for 14 consecutive days** production-access rule applies to new **personal** accounts created after 13 November 2023; it is not a universal organization-account requirement. It is also not a substitute for meaningful testing. [Personal-account testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465). Internal-only apps are exempt from the public Data safety section, but closed/open/production tracks need it; this does not waive secure data handling. [Data safety track scope](https://support.google.com/googleplay/android-developer/answer/10787469).

The next implementation should address items 1–3 before treating a store upload as a public launch. Policy approval is Google's decision and cannot be guaranteed by this review.
