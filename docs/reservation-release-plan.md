## Product decision

Patients reserve a place and receive a server-issued token/check-in QR and an estimated time range. They pay the clinic directly at reception; Kramya does not collect, verify or settle that payment. Staff confirm arrival. Only checked-in patients can be called. A token is a reference, not a guaranteed appointment time or an instruction to delay urgent care.

This supersedes the payment prerequisite in Rules.md, PRD phase 5 and earlier build decisions for NEW reservation-first bookings. Existing gateway payments/refunds retain their signature verification and recovery paths. Never rewrite paid history or applied migrations. New reservations must not create fake SUCCESS payments or use the gateway confirmation command to imply money moved.

## Implementation boundaries

- Additive API first, then backend, native and staff web, then full integration. Existing `CONFIRMED` means an accepted booking, not paid; `paymentStatus: null` must not mean FREE or payment failed.
- No payment UI should remain reachable in the new reservation flow. Preserve legacy payment code until historical transaction/refund obligations and old-client rollout are accounted for; remove unused checkout code after compatibility is proven.
- Use the current session lock, server ownership checks, audit/events and post-commit realtime. No client-issued token, bypassed RLS or broad new database grants.
- Avoid premature reservation expiry based on a moving ETA. Start with explicit session/arrival rules, communicate them before booking, and validate with the pilot clinic. Terminal no-shows do not silently regain their old priority.
- Cash/external UPI payment is clinic-managed. If an acknowledgement field is added, it must distinguish staff-recorded payment from gateway-verified payment, include actor/time and support correction. Do not block clinical care on a payment flag.
- Clinic data entry is self-service by authorized admins; public verification is operator-controlled. No clinic may self-assert VERIFIED through its profile form.
- No new paid service, production deployment, real charge, destructive data cleanup or store registration is part of local implementation. Automatic backup scheduling/retention/alerts remain deferred by the founder; record recovery readiness as a release gate.
- Tests use explicitly isolated local PostgreSQL/Redis. No reset/integration suite against hosted Supabase. Demo UI is excluded.
